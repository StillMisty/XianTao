# ADR-0006: 数据采集与分析闭环

## 状态

已接受

## 背景

数值与内容调整此前依赖人工试玩与静态模拟（`tools/balance/`），缺少线上真实数据的反馈回路：

- 无法回答「实际每级耗时多少、卡在哪」「灵石主要从哪来、花到哪去」「哪个系统没人用」；
- `game_event` 表面向玩家通知，混入叙事模板，不适合作为分析口径；
- 无历史快照，无法做留存、等级驻留与趋势对比。

## 决策

1. 新增 **L0 原始事件表** `analytics_event`（append-only，kind/subject/value/payload JSONB），
   由 `AnalyticsService` 异步批写（业务线程只入队，独立虚拟线程每 2s / 200 条落库，队列满丢弃并计数）。
2. 新增 **L1 每日快照** `player_daily_snapshot`：每小时 upsert 当日快照（当日末次写入为日终态）。
3. 一期埋点（本次）：`command`（指令+耗时+成败）、`breakthrough_attempt/result`、`level_up`、
   `encounter`、`stones_gain/spend`（所有灵石存取带来源/用途词表）。
4. 报告层不落库：`tools/analytics/report.py` 按需从 L0/L1 + 既有业务表计算 Markdown 报告；
   判据与决策动作表见 `tools/analytics/README.md`。
5. 分析数据 **运行时零依赖**：采集失败不影响游戏，表可清空重建；不采用任何主动推送（平台已下线）。

## 理由

1. 唯一「热路径」开销是入队与异步写库，对虚拟线程模型无感知；分析复杂度全部收敛到报告脚本，便于随时改口径。
2. `stones_*` 强制携带来源/用途，是经济分析（产出/消耗比、刷币路径）的前提；错过来源的埋点后续补齐成本高。
3. 快照口径（每人每日一行）使留存、驻留、余额分布等 SQL 简单且廉价，适合当前百级玩家规模。

## 后果

- 每次数值/内容改动后，可用同口径报告对比前后（配合 `tools/balance/` 模拟器：模拟定方向，线上数据验结果）。
- 二期需补：修为/物品账本、阵亡事件、系统渗透率、AI 降级、业务错误码分布（见 README「二期事件」）。
- 报告目前手动生成；若需要每日存档，可加定时任务把结果写入表（暂不做，避免为无消费者的数据买单）。
