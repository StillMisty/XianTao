# Design

## Context

- `docs/` 现有 23 个玩法系统设计文档（约 6,800 行），与 OpenSpec 规格体系并存；`openspec/specs/` 已有 `qq-messaging`、`game-features` 两份契约。
- OpenSpec 能力目录允许 `spec.md` 之外的附加文件（已验证 `openspec validate --specs` 通过），因此可把「契约」与「详细设计」放在同一能力目录下，避免两份记录。
- 用户决定：迁移由子代理执行；**文档与代码冲突时以实际代码为准**。

## Goals / Non-Goals

**Goals:**

- 每个系统一个能力：`spec.md`（行为契约）+ `design.md`（详细设计），单一维护点。
- 契约只描述玩家/外部可观察行为，可被测试或明确验证。

**Non-Goals:**

- 不修改任何业务代码；不调整数值平衡。
- 不改写原文档中的设计意图（仅按代码修正与现状冲突的部分）。

## Decisions

### D1 契约与详情同目录（`spec.md` + `design.md`）

- **理由**：OpenSpec 的 delta 机制只管理 `spec.md`；`design.md` 作为能力目录内的附加文件被工具容忍，既保留公式/表格，又不产生第二套文档树。
- **备选**：把详情压缩进 `spec.md`（丢失公式细节）、另建 `docs/` 文档树（回到双份维护）——均否。

### D2 冲突以代码为准

- **理由**：文档常滞后于实现（本仓库多次出现：文案、门槛、机制与文档不一致）。
- **落点**：子代理先读代码验证再写契约；`design.md` 文末统一记录「与文档的差异（以代码为准）」。

### D3 分批迁移（3 个变更）

- **理由**：23 个能力一次迁移会产生 >10 个 spec delta，评审与校验都不可控。
- **批次**：核心系统（本变更，6）→ 玩法系统（9）→ 社交与基础设施（8）+ 结构清理。

## Risks / Trade-offs

- [子代理对代码理解偏差导致契约错误] → 契约必须能对应到命令/错误码/常量；主代理归档前逐份校验（`openspec validate`）并抽查契约与代码一致性。
- [文档内容在迁移中丢失] → `design.md` 要求「不得丢信息」，差异只允许出现在明确标注的修正段。
- [能力划分过细] → 1 文档 = 1 能力，与现有文档导航一致；后续如需合并可另开变更。
