# Design

## Context

- 延续 `migrate-core-system-docs` 的迁移方式（契约 + 详情同目录、代码为准、子代理执行）。
- 本批 9 个系统与玩家日常循环强相关：炼丹/锻造（产出）、地图/历练/悬赏/运势（成长）、福地/秘境（中期玩法）。
- 其中若干行为已在试玩中暴露过「文档 vs 实现」差异（如秘境列表入口、历练无收益文案、五行属性显示），迁移时以代码为准修正。

## Goals / Non-Goals

**Goals:**

- 9 个能力各自形成可校验契约；详细公式与配置保留在 `design.md`。
- 迁移后删除对应 docs 源文件，`docs/` 继续收缩。

**Non-Goals:**

- 不修改代码与数值；不合并能力。

## Decisions

### D1 与本批一致的目录结构

`openspec/specs/<能力>/spec.md`（契约）+ `openspec/specs/<能力>/design.md`（详情），与核心批次保持一致。

### D2 悬赏/历练的「时间墙」契约写法

契约写玩家可观察规则（时长、结算条件、收益展示、无收益说明），不写定时器/调度实现；实现细节留在 `design.md`。

### D3 冲突修正范围

只修正与代码明确冲突的部分（数值、门槛、文案、入口），设计意图与未实现设想保留在 `design.md` 并标注。

## Risks / Trade-offs

- [本批文档较大（悬赏 314 行 / 秘境 338 行 / 地图 363 行）] → 子代理按能力拆分，逐个核对；主代理抽查契约与代码一致性。
- [运势/福地等含随机机制] → 契约只写「可观察的概率/维度/提示」，不固化随机实现。
