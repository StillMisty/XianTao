# ADR-0004: 命令按玩家串行化执行

## 状态

已接受

## 背景

CommandDispatcher 为每条消息分配一条虚拟线程，同一玩家的多条命令可以并发执行。数据库层的条件更新（`UPDATE ... SET x = x - ? WHERE x >= ?`）只覆盖扣减类操作， 游戏状态机类操作仍存在竞态：

- 连点两次「突破」可能触发两次突破流程；
- 并发「我要修仙」可能重复注册（唯一性检查与写入之间有窗口）；
- 同一活动（历练/赶路/悬赏）的启动与结算交错。

旧 SimBot 实现同样没有串行化，属于既有问题，本次协议重写提供了修复时机。

## 决策

1. 新增 `PerKeySerialExecutor`：按 key 串行、跨 key 并行；队列排空后自动移除尾链条目，内存只与活跃玩家数相关；单任务异常被捕获记录，不阻断后续任务。
2. 在 `CommandDispatcher` 中，命令**匹配之后、认证之前**进入车道，key = `platform:openId`。
3. 未匹配的消息不进入车道（闲聊不占用车道，避免队头阻塞）。
4. 车道键使用 openId 而非 userId：注册等未绑定用户的操作同样需要串行化。

## 理由

1. 竞态都发生在命令执行体内；匹配与认证是只读操作，按 key 串行执行它们不会带来正确性收益，只会放大冲突面。
2. 认证与执行放在同一条车道任务内，`ScopedValue` 绑定天然不跨线程，无需任何跨线程传递机制。
3. 使用 `CompletableFuture` 尾链实现：`compute` 原子更新链尾、`whenComplete` 在锁外清理，空闲即回收，无需额外的淘汰线程或容量上限。

## 后果

### 正面

- 消除同一玩家的连点、双击、重复注册等竞态；命令执行顺序可预期（到达顺序）。
- 不同玩家之间完全并行，单玩家的慢命令不影响他人。
- 未匹配消息不排队，机器人不会被群聊刷屏拖慢。

### 负面

- 同一玩家的长耗时命令（如 AI 对话）会阻塞其后续命令；这是串行化的固有语义。
- 车道是进程内状态，重启即清空；不提供跨进程的分布式串行化（当前单实例部署，满足需求）。

### 注意事项

- GM 命令按**操作者**串行，而不是按目标玩家；跨玩家的多步交互（交易、组队）不属于本机制覆盖范围，需要时另做协调机制。
- 若未来出现「读命令被写命令拖慢」的明确诉求，可再引入只读标记（`@ReadOnly`）绕过车道；当前不预先分类。

## 相关决策

- ADR-0002：匹配 → 认证 → GM 的拦截顺序在本机制内保持不变，整条链路在同一车道任务中执行。
